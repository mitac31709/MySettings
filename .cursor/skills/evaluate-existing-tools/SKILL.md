# 既存ツール調査と自作要否の判断

アプリ、CLIツール、小規模スクリプト、設定補助ツールを新しく作成する前に（ユーザーから指示された場合・エージェント自身が作成しようと考えた場合のいずれも）、まず既存の代替手段を調査して「自作する価値があるか」を検証する。

## 手順

1. **手を動かす前に類似ツールを調査する**
   - 要件と同等以上の機能を持つ既存のアプリ、OSS、標準CLIツール、システム設定オプション（NixOS / Home Manager / `nixpkgs` 等）を探す。
   - Web検索やパッケージ検索などを使い、複数の候補（定番ツール・軽量代替・組込み機能）を洗い出す。

2. **自作案と既存ツールを比較する**
   次の観点で比較し、自作の妥当性を評価する。
   - **要件適合度**: 既存品やその組み合わせ・設定だけで目的を満たせるか
   - **作成コスト**: 設計・実装・検証・ドキュメント整備にかかる手間
   - **維持・管理コスト**: 今後のバグ修正、依存更新、OS/環境変化への追従、独自コードの負債化
   - **既存品の導入コストと信頼性**: 導入・設定の容易さ、メンテナンス継続性、ライセンス、安全性

3. **判断に応じて行動する**
   - **自作コストに見合う価値がない場合（既存品で十分代替できる場合）**:
     - コードやスクリプトは書かない。
     - 調査した既存アプリ／ツールを根拠（特徴・導入方法・自作案と比べたメリット・注意点）とともにユーザーへおすすめとして提案する。
     - エージェント自身の内部判断として作成を検討していた場合も、自作せず既存ツールの利用・導入に切り替える。
   - **作る価値が上回る場合**:
     - 既存の代替案を調べた結果と、それでも自作すべき理由（既存品が存在しない、要件固有で既存品の組み合わせより単純・低保守コストになる、など）を簡潔に説明してから実装に進む。
     - 調査結果を提示したうえでユーザーが明示的に自作を希望した場合も、同様に作成を進める。

## 例外

- 既存ファイルや既存システムへの部分的なバグ修正・設定追記など、新規のアプリ／ツール／スクリプト作成を伴わない作業には適用しない。
- ユーザーから明示的に「既存品ではなく学習や検証のために自作したい」と指定されている場合は、関連調査を簡潔に留めて要求に沿って作成する。
